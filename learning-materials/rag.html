2核心问题

  1. 现场性：大模型参数里没有公司内部文档 / 今天的新闻 / 你那本课本，怎么让它的回答能用到这些"现场信息"？

  3. 区别性：RAG 和"用搜索引擎自己查资料再粘给 AI"看起来很像，它们的差别在哪？

3通俗解释

一句话定义：RAG（Retrieval-Augmented Generation）是一种让大模型在回答之前先去外部知识库"查资料"，再把查到的内容连同问题一起拼进上下文，最后才生成回答的工程模式。

类比：可以把它理解为"开卷考试"——普通大模型是闭卷回答（只能凭参数里背下来的旧知识作答），RAG 则是先允许"翻书查资料"，再把找到的内容摆到桌上，最后综合写成答案。这正好补上了「上下文」那一课的短板：上下文里没有的知识对模型等于不存在。

类比的局限：把 RAG 比作"开卷考试"形象但会让人忽视 RAG 的两大真实难点——检索质量（搜不到对的资料，模型给再多上下文也没用）和上下文组织（检索结果太长会冲淡关键信息，呼应上下文里的 Lost in the Middle 现象）。

关键特征：

  • 知识外置：把模型参数里没有的知识放在外部知识库，更新只需重建索引、不必重训模型
  • 按需检索：每次只把和问题相关的片段送进上下文，避免塞入整本文档
  • 可追溯：答案中的事实可附带引用编号，能反查到原始资料来源
  • 检索 + 生成两步：检索找到"答案的素材"，生成负责整合表述——这是与传统搜索最本质的区别

5应用场景

场景：用 AI 助手帮你做"课程问答机器人"——同学问课程相关问题，机器人只引用课件、教材、老师讲义作答。

图：课程问答机器人的 RAG 流程时序Mermaid · sequenceDiagram
sequenceDiagram
    participant U as 同学
    participant Bot as 课程机器人
    participant E as Embedding
    participant V as 向量库
    participant L as LLM
    U->>Bot: 第二章SVM对偶问题?
    Bot->>E: 问题→向量
    E->>V: 相似度检索
    V-->>Bot: Top-3 课件片段
    Bot->>L: 提示=角色+片段+问题
    L-->>Bot: 基于资料的解答
    Bot-->>U: 答案+引用[1][2]
图读法：注意"问题→向量"这一步——RAG 的关键不是搜索关键词，而是把问题和文档都转成同一空间里的向量，靠相似度找出"语义相关"的片段（即便关键词不重合也能搜到）。最后答案里带 [1][2] 引用编号，是因为答案里的事实都来自检索到的片段——这是 RAG 比"直接问大模型"更可信的核心机制：可追溯。
  1. 课程资料预处理：把所有 PDF 课件、教材章节、老师讲义切成小段，编码为向量，存入向量数据库（这是 RAG 的关键资产）
  2. 同学提问："第二章里支持向量机的对偶问题怎么推导？"
  3. 检索阶段：把问题转成向量，到向量库里找出最相关的 3-5 段教材内容（可能是支持向量机原始定义页+对偶问题推导页+例题页）
  4. 拼接阶段：把这些片段+问题+系统提示（"你只允许引用上述内容作答，不知道就说不知道"）拼成一个 prompt
  5. 生成阶段：LLM 基于这些"现场材料"写出答案，并在每个关键句后标注引用编号
  6. 如果同学追问，模型基于同样检索到的素材继续回答——始终不脱离一手知识

对比"直接问普通 AI"——普通 AI 会一本正经地用参数里模糊的 SVM 记忆给出答案，经常出错；用 RAG 后回答的每一步推导都能追溯到教材页码，对错一目了然。

6概念辨析（易混淆 + 使用边界）

易混淆对比表

易混概念区别一句话
RAG vs 微调RAG 改的是"考试时带的资料"（上下文），微调改的是"脑子里背的内容"（参数）
RAG vs 搜索引擎搜索引擎返回链接让用户自己读；RAG 把检索结果直接喂给 LLM，由 LLM 整合成完整答案
RAG vs 长上下文长上下文是"整本教材摆桌上"（贵、易超出窗口）；RAG 是"先查索引再带几页进考场"（精准、省 token）
RAG vs Agent 工具调用RAG 是"被设计好的检索→生成流水线"；Agent 则会按需动态决定何时检索、用哪个工具、检索几次

常见误解清单

  • 误解："RAG 让 AI 永远正确。" → 正确：RAG 只保证"依据给定的资料"，资料本身错就跟着错；模型仍可能在整合时遗漏或扭曲检索结果。
  • 误解："RAG 一定要用向量数据库。" → 正确：检索手段多种多样：关键词、BM25、Elasticsearch、API 调用都行，向量检索只是当前最流行的一种。
  • 误解："塞满上下文 = RAG。" → 正确：真正的 RAG 必须有"针对当前问题检索最相关片段"的过程；整段粘贴只是长上下文，不是 RAG。

使用边界（什么时候不该用 RAG）

  1. 检索不到相关资料时，RAG 不如直接让 LLM 自由发挥（瞎答有时比"我说不知道"更有用）；
  2. 检索结果过多会稀释上下文，反而降低质量，要限制 Top-K；
  3. 资料源必须新鲜且权威，否则 RAG 拉的是最新的谣言；
  4. 极简单问答用 RAG 反而绕远、增加延迟和成本。

1.（单选）RAG 的四个核心步骤，最准确的顺序是？

正确答案：B。提问 → 检索 → 拼上下文 → 生成。

答错反馈：A（"检索→提问→生成→拼"）把"提问"放在"检索"之后，逻辑反了——没有用户问题，检索什么？C（"生成→检索→拼→生成"）出现两个"生成"，步骤重复且顺序错。D（"拼→检索→生成→提问"）先拼再检索，等于凭空拼上下文，毫无依据。

2.（单选）"把 8000 字课程讲义整段贴给 AI 提问"算 RAG 吗？
A. 算，是简化的 RAG　B. 不算，是长上下文　C. 算，是检索的特例　D. 都不算

正确答案：B。整段粘贴没有"按问题检索相关片段"这一步，只是把所有可用知识一股脑塞进上下文窗口。真正的 RAG 必须有"针对当前问题检索最相关片段"的过程。

答错反馈：A（"算，是简化的 RAG"）把"塞满窗口"误以为就是 RAG——RAG 的关键不是"用资料"，而是"按问题找最相关的资料"。C（"算，是检索的特例"）混淆了"检索行为"和"按需检索机制"——整段粘贴没有"按需"动作。D（"都不算"）虽然承认它不是 RAG，但忽略了它属于"长上下文"这一具体技术类别。

3.（单选）RAG 的答案能附引用编号（如 [1][2]）的根本原因是？

正确答案：C。答案中的事实都来自检索到的片段，因此每条事实都能反查到原始资料来源。

答错反馈：A（"AI 主动加的"）只对了一半——AI 确实"主动"加，但前提是它"有据可加"。B（"检索结果自带编号"）是工程实现细节，与"为什么能加"的根因不同。D（"用户要求"）混淆了机制与触发——用户要求是触发条件，但根本机制是事实可追溯。

4.（简答）RAG、微调和长上下文三种"让模型掌握新知识"的方法各有什么取舍？

正确答案：RAG：即时更新、成本中等、改的是每次提问的上下文；微调：耗时长、贵、改的是模型参数（长期记忆）；长上下文：实现最简单但受窗口限制、token 成本高、知识"塞"在 prompt 里。三者常组合使用。

常见漏答：① 只罗列方法没说取舍——题目要的是权衡分析；② 把 RAG 和"塞上下文"混为一谈——前者有检索步骤，后者没有。

回到正文：板块 4「与三个相近概念的关系」表格。

5.（简答）RAG 不是万能的——什么时候用 RAG 比直接问 LLM 更糟？

正确答案：① 检索库没有相关资料时（强行 RAG 会让模型无依据作答或答非所问）；② 检索质量差、Top-K 命中无关内容时（反而污染上下文）；③ 文档质量差 / 有错误时（模型会被错误信息引导，比直接问更糟）；④ 极简单问答（用 RAG 反而绕远、增加延迟和成本）。

常见漏答：① 只回答"资料不好"不说具体场景——题目要的是"何时"；② 漏掉"极简单问答"这条——这是容易被忽视的成本边界。
