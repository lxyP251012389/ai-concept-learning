# 概念学习资料生成 Skill（concept-learner）

把"如何系统学习一个新概念"沉淀成可复用的流程：检索 → 结构化 → 通俗化 → 自检。
任何人（包括未来的我）给出一个新概念，都能用同一套方法产出质量稳定的学习资料。

## 一、适用场景

- 学到一个新概念（技术名词、课程术语、工具机制），想系统整理成学习资料
- 课程预习 / 复习，需要结构化笔记而不是碎片化搜索结果
- 想要"讲人话"的解释 + 可核查的来源，而不是名词堆砌
- 需要自测问题来检验自己是否真的学会了

## 二、输入信息

| 输入项 | 必填 | 说明 | 默认值 |
|--------|------|------|--------|
| 概念名称 | ✅ | 要学习的概念，如"大模型的上下文" | 无 |
| 输出文件名 | ❌ | learning-materials/ 下的文件名 | 概念英文名的 kebab-case，如 `llm-context.html` |
| 学习深度 | ❌ | `入门` 或 `进阶` | 入门 |
| 重点关注 | ❌ | 希望额外展开的角度，如"与其他课程概念的关系" | 无 |

## 三、生成步骤

1. **理解概念**：先明确概念的定义、所属领域、常见使用语境；如果概念有歧义（一词多义），先列出主要含义并说明本资料采用哪个。
2. **检索来源**：通过网络搜索查找 **2–4 个权威来源**，优先级：官方文档 > 经典论文（arXiv 等）> 厂商技术百科 / 知名工程师博客。**逐条实际访问**，确认 HTTP 200 且内容相关，记录 URL 与访问日期。**禁止编造任何来源。**
3. **结构化组织**：严格按照下方"输出结构"的八个板块组织内容，不得缺项、不得调换顺序。
4. **通俗转写**："我的解释"必须用第一人称、大白话重写，可以使用类比，但类比必须标注"类比"，并说明类比的局限（哪里像、哪里不像）。
5. **设计可视化**：按下方"可视化规范"为第 4、5 板块设计配图——优先 Mermaid 流程图 / 思维导图 / 时序图 / 概念图，复杂结构辅以对比表。
6. **生成 HTML**：输出为**自包含**的 HTML 文件（内联 CSS；可视化用 Mermaid `<pre class="mermaid">` 块 + Mermaid CDN，可在 HTML 顶部加一行说明），保存到 `learning-materials/<输出文件名>`。整体风格与本仓库已有资料保持一致。
7. **自检**：执行下方"自检清单"，逐项核对，全部通过才算完成。
8. **交付**：把生成的文件展示给用户预览，**明确提醒用户进行人工核查**（核对事实、改写个人解释、补充自己的理解、审阅 Mermaid 图是否准确表达了你的意思），并建议把核查记录写进 README。

## 四、输出结构（八个板块，缺一不可）

1. **学习目标** —— 学完这份资料后应能回答的问题，3–5 条，用"能说出 / 能区分 / 能解释 / 能举出"等可检验动词开头。
2. **核心问题** —— 直击概念本质的 2–3 个问题，先问后学，带着问题读正文。
3. **我的解释** —— 第一人称、通俗的个人解释，100–200 字。禁止照搬来源原文；必须用自己的话。
4. **核心机制 / 组成** —— 把概念拆成组成部分或运行机制，**至少配一张可视化图**（按"可视化规范"选用 Mermaid 流程图 / 思维导图 / 时序图 / 概念图 / 状态图，复杂结构辅以对比表）。
5. **应用场景** —— 一个具体的、贴近课程或生活的场景，**配一个"概念在其中如何发挥作用"的可视化流程**（Mermaid 时序图或流程图最佳），按步骤走一遍。
6. **概念辨析** —— 与 2–3 个容易混淆的近义概念做对比（表格：维度 × 概念），并明确写出**使用边界**（什么时候该用 / 不该用、常见的错误理解）。
7. **自测问题** —— 5 道题（选择 / 简答混合），提供参考答案，答案默认折叠。
8. **参考来源** —— 2–4 条真实链接，每条注明：来源名称、URL、**访问日期**、该来源支撑了资料中的哪部分内容。

## 四之五、可视化规范

**目的**：让抽象概念"看一眼就懂"，降低理解门槛；也让用户能直观对照自己的理解是否正确。

**优先级**：Mermaid 图 > 内联 SVG > ASCII 文本图。Mermaid 写法可读、易维护、AI 写得准、人审得过来，是首选方案。

**Mermaid 使用规范**：

1. **HTML 末尾引入一次**：
   ```html
   <script src="https://cdn.jsdelivr.net/npm/mermaid@10/dist/mermaid.min.js"></script>
   <script>mermaid.initialize({ startOnLoad: true, theme: 'neutral', securityLevel: 'loose' });</script>
   ```
   在 HTML 顶部 `<head>` 内加一行提示"本文件包含 Mermaid 图表，需联网渲染；离线时显示源代码"。

2. **每张图用 `<pre class="mermaid">...</pre>` 包裹**，代码块本身即可读（不渲染时也能看懂）。

3. **可用图类型与典型场景**：

   | 图类型 | Mermaid 语法 | 典型场景 |
   |--------|---------------|----------|
   | **流程图** | `flowchart LR/TD` | 概念的工作流程（如 RAG：索引→检索→生成；Agent：感知→思考→行动→观察） |
   | **时序图** | `sequenceDiagram` | 多角色交互（用户↔Agent↔工具；模型↔Skill↔上下文） |
   | **状态图** | `stateDiagram-v2` | 状态机（上下文窗口的填充与裁剪；Skill 的加载/未加载/匹配触发） |
   | **概念图** | `graph LR` + 节点连线 | 概念间关系网（多个概念如何咬合、谁影响谁） |
   | **思维导图** | `mindmap` | 概念的组成维度或分支（大模型上下文的五要素） |
   | **甘特图** | `gantt` | 任务时间线（仅当资料涉及步骤时序才用） |

4. **写法要求**：
   - **节点文字 ≤ 6 个汉字（或 3 个英文单词）**，长文字会让图变丑；必要时拆成多个节点
   - 箭头方向**有明确语义**：实线=数据/控制流，虚线=反馈/迭代
   - **关键节点用粗框/高亮**突出主线，让眼睛先抓主干再看分支
   - **配色与已有资料保持一致**：主线 `#2563eb`（蓝）、次线 `#7c3aed`（紫）、反馈 `#b45309`（橙）、环境 `#0e7490`（青）

5. **降级方案**：Mermaid CDN 不可用时，图块会显示原始 Mermaid 代码（仍可读懂），所以**永远不要把信息只藏在图里**——表格或文字说明必须紧随其后。

6. **每个 Mermaid 图后必须配一段文字解读**（2–4 句）：解释图的阅读顺序、关键节点含义、把图映射回正文论述。避免"图自图、文自文"。

**何时不用图**：
- 概念非常简单（如"整数"），表格已足够
- 图会让读者分心而非聚焦（信息密度过高、节点数 > 10）
- 该用对比表表达对照关系时，不要强行画图

## 五、资料来源要求

- 只使用**真实存在、可公开访问**的链接，生成前必须逐条访问验证（HTTP 200）
- 优先级：官方文档 > 经典论文 > 厂商技术百科 / 知名工程师博客；拒绝内容农场
- 每条来源标注访问日期（格式：YYYY-MM-DD）
- **禁止编造**论文、作者、URL、数据；禁止把"听说"写成"事实"
- 当不同来源说法冲突时，以官方文档为准，并在资料中注明分歧
- 来源数量不足 2 个时，宁可暂停并向用户说明，也不要用不可靠来源凑数

## 六、自检清单（交付前逐项打勾）

- [ ] 八个板块齐全，顺序正确，无缺项
- [ ] "我的解释"是第一人称大白话，不是名词堆砌，也不是来源原文复述
- [ ] "概念辨析"至少对比 2 个易混概念，并写明了使用边界
- [ ] **第 4 板块"核心机制"至少配 1 张可视化图**（Mermaid 流程图/思维导图/概念图等），图后有文字解读
- [ ] **第 5 板块"应用场景"配有可视化流程或时序图**，把概念如何发挥作用画出来
- [ ] **Mermaid 图通过自检**：节点文字短（≤ 6 汉字）、箭头语义清晰、关键节点突出、配色与已有资料一致；图后紧跟 2–4 句解读
- [ ] 所有参考链接实际访问过（HTTP 200），标注了访问日期
- [ ] 自测问题有参考答案，答案默认折叠
- [ ] HTML 自包含：除 Mermaid CDN 外无其他外链 CSS / JS / 图片，离线时图块显示源代码而非空白
- [ ] 文件已保存到 `learning-materials/` 目录，命名与已有文件风格一致
- [ ] 已提醒用户人工核查（含 Mermaid 图是否符合个人理解），并告知核查结果要记入 README

## 七、示例调用

> "用 concept-learner 学习一下『检索增强生成（RAG）』这个概念，重点关注它和大模型上下文的关系。"

预期产物：`learning-materials/rag.html`（八板块齐全 + 3 条可核查来源 + 访问日期）。

## 八、使用经验与迭代记录

本节记录 Skill 在实际使用中发现的新约束或更好的做法，用以沉淀团队/个人知识。后续每次使用后，建议追加一条。

- **2026-09-04 RAG 应用经验**：
  1. 在生成"和已有概念强相关"的概念（如 RAG ↔ 上下文、Agent ↔ Skill）时，应在「我的解释」中**显式回链**到已有概念（指向已生成的 HTML 文件名），让概念网络逐步长出来，而不是各管各的散点；
  2. 当使用方处于受限网络（频繁 502）时，**生成阶段不要试图访问网络**——来源验证可在生成前用 `curl` 一次性批量跑完并保存本地清单**，避免 8 个来源逐个 502 把生成流程拖垮；
  3. 「自测问题」的"易混题"答案应写得**比教材还直白**，因为用户常在答错后才来对答案，参考答案的"可读性"比"严谨性"更优先；
  4. 每次使用后，把新发现的规则直接追加到本节，让 Skill 越用越聪明——这正是 Skill 的核心价值：**把一次性的好做法沉淀成可复用的方法论**。
- **2026-09-10 可视化经验**：
  1. **Mermaid 取代 SVG 优先**：手写 SVG 改一处要重画整张图，维护成本高；Mermaid 文字描述图结构，可 diff、可复用、AI 写得准人也审得过来——本仓库四份资料的关系图均可逐步迁移到 Mermaid；
  2. **节点文字必须短**：第一版常把整段话塞进一个节点，结果图变"墙"；正确做法是节点只放关键词 + 旁边表格补全细节；
  3. **图后必跟解读**：图说明的是结构，解读说明的是含义；两者缺一就会"图归图文归文"；
  4. **CDN 不可用是常态，不是异常**：用 `<pre class="mermaid">` 包裹让 CDN 失败时显示源代码即可——这就是为什么"信息不能只藏在图里"；
  5. **可视化不等于好看**：判断标准是"看完图比看完正文更快理解结构"，不是"图漂亮"；节点数 > 10 时应拆成多图或改用表格。
- **2026-09-10 可视化落地记录**（上面 5 条规则的执行验证）：
  1. 把 5 份资料的"应用场景"板块（agent.html 137、llm-context.html 130、skill.html 147、rag.html 145、concept-relationship.html 板块 6 "闭环实例"）各补 1 张 Mermaid 时序图，配 2-4 句图后解读；
  2. 选型：时序图优先于流程图——Agent、上下文、Skill、RAG 都是多角色交互，"谁什么时候做了什么"用时序图最直观；
  3. `<head>` 加一次性 Mermaid CDN 引入，CDN 不可达时图表块显示源代码而非空白（用户不会丢失任何信息，只是少了一张图）；
  4. CSS 加 `.figure` / `.mermaid` / `.mermaid-legend` 三类样式，让图块有边框、有图题、有解读区，与已有 SVG 风格一致；
  5. 第 4 板块原有 SVG 机制图保留不动（已满足"至少配 1 张可视化图"的硬性要求），未来可二次迭代统一为 Mermaid——这次先保功能、风格留作渐进优化；
  6. **自检清单强化**：本节新增的规则应同步写进第六节「自检清单」（已在上面 113 行体现："第 5 板块配有可视化流程或时序图"），避免 Skill 文档与执行脱节。
